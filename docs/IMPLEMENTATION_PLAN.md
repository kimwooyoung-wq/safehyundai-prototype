# SafeHyundai 앱 시연 프로토타입 구현 계획서

## 1. 목표와 성공 조건

SafeHyundai의 목표는 기능을 많이 나열하는 것이 아니라, **차량이 현재 주행 맥락을 이해하고 운전자에게 필요한 경험을 적절한 시점에 제공한다**는 가치를 한 번의 시연으로 이해시키는 것입니다.

프로토타입 성공 조건은 다음과 같습니다.

1. 한 화면에서 지도와 차량 맥락 패널이 안정적으로 동작한다.
2. 시나리오 시작 후 차량 데이터가 시간에 따라 바뀐다.
3. 음악 추천, 풍경 기록, 인수인계, 안전 요약 중 최소 3개가 서로 연결된다.
4. 실제 차량 신호와 모의 데이터의 경계가 문서와 화면에서 명확하다.
5. 인터넷이나 외부 API가 끊겨도 심사 시연이 끝까지 재현된다.
6. 3분 이내에 문제–기능–효과–확장 가능성을 설명할 수 있다.

## 2. 사용자와 핵심 문제

### 주 사용자

- 장거리 또는 여행 운전자: 운전 중 조작을 줄이고 여행 경험을 남기고 싶은 사람
- 가족·연인·친구와 동승하는 운전자: 음악과 풍경 기록을 함께 공유하고 싶은 사람
- 가족 차량이나 공유 차량 사용자: 이전 운전자가 발견한 차량 상태를 정확히 넘겨받고 싶은 사람

### 해결할 문제

- 운전 중 음악 탐색과 기록 조작은 주의를 분산시킨다.
- GPS, 음악, 사진, 차량 상태가 서로 다른 앱에 흩어진다.
- 차량 인수인계가 구두나 메신저에 의존해 누락되기 쉽다.
- 주행 피로와 반복되는 위험 패턴을 운전자가 객관적으로 보기 어렵다.

## 3. 기능 범위

### P0: 심사 시연에 반드시 포함

#### 3.1 Drive Mood

- 입력: 주행 시간, 속도 변화, 목적지 유형, 날씨, 사용자 선호
- 처리: 명시적인 규칙 점수로 `도심`, `장거리`, `휴식`, `여행` 모드 선택
- 출력: 실제 앨범 이미지와 곡명, 선택 이유, 재생/일시정지
- 안전 원칙: 운전 중에는 곡 목록 탐색 대신 한 번의 추천과 큰 조작 버튼만 제공

예시 규칙:

```text
주행 시간 >= 45분 AND 급가속 빈도 낮음 AND 목적지가 여행지
→ 장거리 여행 모드
→ 사용자가 선호한 잔잔한 곡 중 BPM 80~110 추천
```

#### 3.2 Drive Memory

- 입력: GPS 위치, 풍경 기록 버튼, 촬영 시각, 당시 재생 곡
- 처리: 같은 구간의 기록을 하나의 여행 이벤트로 묶음
- 출력: 풍경 사진, 장소, 곡, 짧은 설명이 포함된 타임라인 카드
- 프로토타입에서는 실제 카메라 자동 촬영 대신 사용자가 누르는 `풍경 기록` 버튼과 준비된 이미지 사용

#### 3.3 Car Relay

- 입력: 하차 시 음성 메모 또는 준비된 대본, 차량 상태 값
- 처리: 음성을 텍스트로 변환한 뒤 `타이어`, `연료/배터리`, `경고등`, `정비`, `기타`로 분류
- 출력: 다음 운전자에게 우선순위, 발생 시각, 확인 여부가 있는 인수인계 카드 제공
- 데모 예시: “운전석 앞바퀴 공기압이 낮았어요.” → `타이어/주의` 분류

#### 3.4 Drive Guardian

- 입력: 주행 시간, 급가속/급감속, 정차 빈도, 평소 기준
- 처리: 운전자별 기준선과 현재 세션의 차이를 계산
- 출력: 운전 중 최소 알림, 주행 종료 후 피로 및 주행 패턴 요약
- 의료 또는 사고 예측으로 표현하지 않고 운전 습관 안내로 한정

### P1: 데모 품질 향상

- 사진 여러 장으로 여행 앨범 생성
- 인수인계 확인/해결 처리
- 시나리오 선택 화면
- 주행 종료 리포트 공유 이미지
- 다크/라이트 전환과 야간 지도

### P2: 실제 연동 검증 후

- Pleos 차량 신호 실시간 수신
- 실제 내비 목적지와 ETA 수신
- 시스템 미디어 플레이어 제어
- 운전자 프로필과 공유 차량 계정 동기화
- 서버 기반 다중 사용자 인수인계

## 4. 구현 전략

### 4.1 데모 우선 원칙

첫 구현은 서버와 실제 차량 없이 브라우저에서 완결합니다. 외부 API 실패가 시연 실패로 이어지지 않도록 지도, 음원 메타데이터, 차량 신호, 날씨를 로컬 시나리오에 포함합니다.

### 4.2 어댑터 교체 구조

UI는 `VehicleDataPort`, `NavigationPort`, `MediaPort`, `SpeechPort`, `WeatherPort` 인터페이스만 사용합니다. 프로토타입에서는 `Mock*Adapter`, 공식 연동 단계에서는 `Pleos*Adapter`를 주입합니다. 이 방식은 SafeRoad에서 사용한 데이터 수집과 분석의 분리 원칙을 앱 시연 규모에 맞게 단순화한 것입니다.

### 4.3 규칙 기반 AI부터 시작

공모전 시연에서 중요한 것은 모델 규모가 아니라 판단 근거의 이해 가능성입니다. 추천과 분류는 먼저 규칙 기반으로 구현하고, 화면에 “장거리 주행 48분 + 여행 목적지”처럼 추천 근거를 표시합니다. 로그가 쌓인 뒤 개인화 모델로 교체할 수 있습니다.

### 4.4 지도 구현

- 1차: 현재 Figma와 유사한 한양대역–중랑천–뚝섬역 구간을 로컬 SVG 지도 자산으로 제작
- 경로: SVG path와 진행률을 결합해 이동 애니메이션 표현
- 교통: 녹색/주황색 선을 시나리오 값에 따라 표시
- 2차: MapLibre 또는 공식 지도 SDK를 `NavigationPort` 뒤에 연결

로컬 지도는 실제 길찾기 정확도를 주장하기 위한 것이 아니라 데모 안정성을 위한 것입니다. 실시간 길찾기로 오인되지 않도록 화면 하단 또는 README에 `시뮬레이션 경로`를 표기합니다.

## 5. 화면 구성

### 5.1 기본 HMI

- 상단: 변속 상태, 주행 가능 거리, 연결 상태, 시간
- 왼쪽 70~75%: 지도, 경로, 회전 안내, 속도
- 오른쪽 패널: 선택한 기능의 상세 정보
- 우측 세로 Dock: 홈, 지도, 음악, 기록, 인수인계, 차량
- 하단: 공조 상태와 최소 조작

### 5.2 우측 패널 우선순위

패널은 동시에 여러 카드를 쌓지 않고 한 가지 맥락을 우선 표시합니다.

| 우선순위 | 상태 | 표시 내용 |
|---:|---|---|
| 1 | 차량 주의 | 경고 아이콘, 인수인계, 확인 버튼 |
| 2 | 휴식 권고 | 이유, 다음 휴게 지점, 나중에 버튼 |
| 3 | 풍경 기록 | 촬영 이미지, 장소, 재생 곡, 저장 상태 |
| 4 | 음악 | 앨범, 곡, 추천 이유, 재생 제어 |
| 5 | 기본 | 차량 상태 아이콘과 주행 모드 |

## 6. 데이터 설계

### 6.1 공통 차량 상태

```ts
type VehicleSnapshot = {
  timestamp: string;
  speedKph: number;
  odometerKm?: number;
  rangeKm?: number;
  batteryPercent?: number;
  fuelPercent?: number;
  gear: 'P' | 'R' | 'N' | 'D';
  warningCodes: WarningCode[];
  tirePressureKpa?: Record<'fl' | 'fr' | 'rl' | 'rr', number>;
};
```

### 6.2 주행 이벤트

```ts
type DriveEvent =
  | { type: 'TRIP_STARTED'; at: string }
  | { type: 'SCENIC_POINT'; at: string; locationId: string }
  | { type: 'HARD_BRAKE'; at: string; severity: 1 | 2 | 3 }
  | { type: 'WARNING_CHANGED'; at: string; codes: WarningCode[] }
  | { type: 'VOICE_RELAY_SAVED'; at: string; relayId: string }
  | { type: 'TRIP_ENDED'; at: string };
```

### 6.3 저장 범위

- 브라우저 세션: 실시간 차량 값과 현재 UI 상태
- IndexedDB: 저장한 풍경 기록, 인수인계 카드, 최근 주행 요약
- 커밋 금지: 실제 음성 원본, 전화번호, 이메일, API 키, 개인 위치 기록

## 9. 테스트 계획

### 단위 테스트

- 장거리/여행 조건에서 올바른 주행 모드가 선택되는가
- 경고 코드와 음성 대본이 올바른 인수인계 범주로 분류되는가
- 급감속/주행시간으로 Guardian 점수가 기대 범위에 있는가

### 통합 테스트

- `MockVehicleAdapter` 이벤트가 Zustand 상태와 UI까지 전달되는가
- 풍경 기록에 현재 위치와 재생 곡이 함께 저장되는가
- 시나리오 초기화 후 이전 데이터가 화면에 남지 않는가

### 시연 안정성 테스트

- 오프라인 상태에서도 처음부터 끝까지 실행 가능한가
- 1920×1080, 1366×768에서 패널이 잘리지 않는가
- 새로고침 후 데모 시작 상태로 복구 가능한가
- 모든 핵심 버튼이 운전자 화면에서 충분히 큰가

## 10. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| Pleos SDK 접근 불가 | 실차 데이터 시연 불가 | 모의 어댑터로 완결, 연동 필요 항목 별도 표시 |
| 지도 API 키/네트워크 실패 | 데모 중 빈 지도 | 로컬 SVG 지도를 기본값으로 사용 |
| 브라우저 STT 불안정 | 음성 인수인계 실패 | 사전 녹음/대본 선택 버튼 제공 |
| 기능 과다 | 화면 복잡, 설명 시간 초과 | 우측 패널 한 상태 원칙, 3분 시나리오 고정 |
| 개인정보 노출 | 심사/공개 저장소 위험 | 샘플 데이터만 사용, 원본 신청서 커밋 금지 |
| AI 과장 | 신뢰도 저하 | 규칙과 판단 근거를 공개하고 의료/사고 예측 표현 금지 |

## 11. 완료 정의

프로토타입은 다음 조건을 모두 만족하면 `DEMO` 상태입니다.

- 로컬 실행 명령 한 줄로 시작된다.
- 심사 시나리오 3개가 각자 초기화 가능하다.
- 지도, 음악, 풍경 기록, 인수인계가 최소 한 흐름으로 연결된다.
- 외부 네트워크 없이 동일한 결과가 재현된다.
- 실제 연동과 모의 데이터가 README와 화면에서 구분된다.
- 핵심 테스트가 통과하고 90초 이상 시연 영상이 존재한다.
